Finding and correction
The previous native_windows.go nativeUnmap kept m.handle nonzero after a
CloseHandle error, then retried that numeric handle on another managed Close.
The MapViewOfFile rejection branch also called CloseHandle directly and placed
the unchanged mapping record into native.retained on error. Both paths could
therefore repeat an uncertain mapping-object close through nativeClose, although
main-file and metadata handles already used terminal-uncertainty state.
This flaw was present in the immutable basis; the old basis alone does not meet
the no-raw-retry claim. No native error was induced to find or qualify it.

The correction routes both paths through mappingRetirement.retire:
- nativeMap lines 680-685 uses nativeUnmap for failed-view cleanup and retains the
  complete nativeMapping record if cleanup is unresolved.
- nativeUnmap lines 692-706 uses the same portable transition for published
  mappings, failed-acquisition retained records, and subsequent explicit closes.
- mapping_retirement.go lines 19-30 latches the first poisoned close error once.
  Every later attempt returns that stored error before any raw close or unmap.
  The uncertain handle, view base, length, and owning File remain represented.
- Object-handle close precedes view unmap. Its known success clears only the
  handle. If view retirement then fails, base/length and exposed Bytes remain
  available to the owner, and only the represented view is retried.
- Full retirement clears base/length and is idempotent. No raw handle is exposed
  through a new API, no finalizer or background sweep is introduced, and existing
  File.mu continues to serialize the state.

Retained-view/protector contract
Mapping.retireLocked clears Bytes and removes its owner-map entry only after
nativeUnmap succeeds. File.closeResourcesLocked never closes its descriptor/DMS
while a mapping remains unresolved. nativeClose similarly stops at a retained
failed-acquisition record before descriptor/lock release. The new terminal
state deliberately may retain the view, object tombstone, and protecting file
locks for process lifetime. This is fail-closed availability loss, not a promise
that an uncertain native close can be repaired.

Behavioral review and exact checks
All five new TestWindowsMappingRetirementMemory* laws use synthetic integers,
ordinary Go byte slices, and memory callbacks only. They cover terminal close
repetition 1,000 times; no view unmap after uncertain object close; retryable view-only
retirement after successful object close; failed view acquisition with known or
terminal object retirement; published Bytes plus DMS/main/slot preservation;
independent sibling retirement; and empty/success idempotence. No real native
mapping, raw descriptor, forced error, or filesystem mutation is involved.
