Findings supplied to the source owner
------------------------------------
W1. Frozen18 live os.Lstat + os.SameFile probes bypassed managed ownership.
    namespace.check, inventory, checkedFile and stableFile could enter pinned
    Go os/types_windows.go loadFileId: raw CreateFile followed by deferred
    CloseHandle with its result discarded. os/stat_windows.go has additional
    raw metadata fallbacks. Those resources did not reserve encryptedWinOwners
    capacity or retain unknown-close state. This contradicted all-handle bounded
    lifetime claims. Source-only finding; no failure was executed.
    Owner fix inspected: Windows canonicalPath uses a managed directory and
    GetFinalPathNameByHandle; platformPathInfo uses managed relative metadata
    handles; platformDirectoryCheck compares managed full native IDs; common
    encstore no longer calls path-based os.Lstat/Stat/EvalSymlinks on Windows.
    Remaining os.SameFile inputs are handle-derived FileInfo, whose Go fileStat
    already has identity and does not lazily open another handle.

W2. Main basenames admitted up to 255 UTF-16 units could fail after lock creation
    when the first generated candidate exceeded the NTFS component limit.
    The longest suffix is '.gse-' + 64 hexadecimal units + '.retained' = 78 units.
    A 200-unit main name fit the initial lock name but not generated members.
    Owner fix inspected: windowsFamilyNameBound rejects more than 177 units
    before any native open, provider acquisition or stable-lock creation.
    Supplementary characters count as two UTF-16 units. This conservative bound
    also applies to archive/plain-output targets routed through canonicalPath.

W3. Source owner independently found case-sensitive family classification could
    omit existing history after case-alias reopen. Reviewed the owner's fix:
    native CompareStringOrdinal(ignoreCase=1) normalizes only root/family prefix;
    exact canonical lowercase hexadecimal ID and suffix grammar remains enforced.
    Native Unicode comparison is compile/source evidence, not executed here.

W4. inventory redundantly opened a named directory before its relative open,
    discarding the first Close result. Owner removed that unnecessary open.
    Final fix inspected: inventory joins its deferred enumeration Close result
    into the returned error and resets its byte total to zero on cleanup failure.
    Windows directory public validation also checks closed/poisoned state before
    and after opening its managed named probe; private retained probes remain
    allowed while existing children protect the physically live parent.

Adjacent plain-Windows observation, separately reported to parent
----------------------------------------------------------------
This encrypted review does not repair or certify plain Windows storage.
Source inspected at 2026-10-10 14:49 UTC also showed hidden path-identity opens
at pager/shared_session.go checkStableLocked, walindex/index.go statLocked, and
vfs/file.go validatePathLocked. The latter ran generic named/parent Stat/Lstat
and SameFile after nativeValidatePath. native_windows.go nativeValidatePath also
opened raw metadata handles, reported CloseHandle errors but retained no record
of unresolved probes. Therefore the plain VFS all-probes-use-managed-owner
comment was too broad. Windows locks are per handle; closing a metadata alias
does not itself release another handle's locks. This is an exceptional-resource
representation/failure-reporting gap, not observed data loss or native runtime
failure. Parent owns any separate correction/fix and release evidence.

Final source-review conclusions
------------------------------
- Private Windows managedFile never exports its raw handle. Each native open
  reserves capacity before opening and adopts before validation. Every live
  explicit encrypted file/directory/probe follows that path. Directory lifetime
  is pinned by physically live children; the public closed bit is never cleared.
- Unknown os.File.Close is terminal and retained. Native unlock cleanup remains
  retryable only through the represented exact records. Registry capacity keeps
  unresolved ownership bounded; it does not supply eventual retirement or make
  a dropped caller retry route recoverable. Generic failed-open cleanup can still
  return the original error while an exceptional resource is privately retained.
- Byte 0/1/2 ledger and exact unlock calls preserve successful acquisitions.
  Same-mode repeats are idempotent; downgrade adds shared before releasing
  exclusive; no unprotected shared-to-exclusive unlock/relock emulation exists.
- Live opens/rename use retained directory authority and one validated basename.
  Empty relative ObjectName represents inventory's directory self-open. Native
  full IDs and reparse/link/type/deletion checks are distinct from name matching.
  The publication root alone uses normal delete sharing; immutable members and
  stable lock do not. Metadata/rename probes share delete access. No path-based
  rename/copy/delete fallback appears in the native publication path.
- Early unsupported shared rekey is before Prepare's canonicalization/provider
  call and before BeginMaintenance writer reservation. Legacy-to-shared upgrade
  retains exclusive lifecycle until successful publication then downgrades.
- platform_linux.go remains byte-identical to the saved baseline. Common helper
  refactoring keeps Linux path/identity operations and passed the selected
  correct-key regressions. Inventory now propagates enumeration cleanup errors;
  this source-level error-reporting improvement is not an executed fault test.
- File Sync follows FlushFileBuffers. Directory Sync intentionally performs no
  flush and supplies no namespace persistence guarantee. M3/M8/M10 gates remain
  unsatisfied by this bounded compile/source/memory checkpoint.
